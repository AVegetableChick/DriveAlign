# S11 训练加速决策文档（时间序）

> 目的：记录 S11 冒烟阶段暴露的**全量 SFT 吞吐不可接受**问题，以及逐项落地的加速决策。
> 每项按"物理直觉 → 使用方式 → 调参影响 → 定值依据 → 代价与风险 → 落地"组织，
> 便于 S12 全量 SFT 直接复用。
> 触发背景（**A1 落地前**的读数）：RTX 4080 SUPER（32GB）上，原生分辨率、batch=1、
> grad-accum=4 实测 ≈4.5 s/micro-batch；全量 train split **22,941 帧**折算 **≈29 h/epoch**
> （3 epoch ≈87 h），不可接受。→ 该问题已由 A1 解决（≈5.65 s/step），见 A1 节。
> 关联文档：[S11_implementation_plan.md](S11_implementation_plan.md)、
> [S11_decision_log.md](S11_decision_log.md)、[S11_bug_log.md](S11_bug_log.md)。

## 问题定性：成本主项是"视觉 token"，不是模型参数量

实测数据（单帧 CAM_FRONT，源图 1600×900，**均为 A1 落地前的原生分辨率读数**）：

- 单帧 `pixel_values` = `(7296, 1176)` → patch 7296 → **visual token 1824**
- 整条序列 `input_ids` = 2384 → **视觉 token 占 77%**
- batch=1 时显存已吃到 **31.5 / 32.7 GB（96%）**，GPU util 72%

结论：ViT 的 patch 数与解码器对视觉 token 的注意力同时被图像分辨率支配，
**降低分辨率是唯一能同时压缩"算力 + 显存"的杠杆**。

> **A1 落地后复查**：上表的 token 数与显存占用都已被 A1 改写——视觉 token 1824→448、
> 序列 2384→1008、峰值 reserved 15.08 GiB（不再"吃满 96%"）。
> 另需修正原句的后半截"显存释放后才能谈加大 batch"：**A1 确实释放了显存，但 A2 实测
> 证明加大 batch 并不提速**（bs=2 反而更慢），故 batch 维持 1 —— 见 A2 与 D5。

### 全量训练时间外推（按当前 train32 训练速度）

train32 实测（原生分辨率、`per_device_train_batch_size=1`、`gradient_accumulation_steps=4`、
2 epoch）：`train_runtime = 290.86 s`，覆盖 32 样本 × 2 epoch = **64 个 micro-batch**
（每 micro-batch = 1 个样本的前向+反向），对应 **16 次参数更新**。

单量纲换算：

- 单 micro-batch = 290.86 / 64 ≈ **4.54 s**
- 单次参数更新 = 290.86 / 16 ≈ **18.18 s**

全量 train split = **22,941 帧**，按"每样本一次 micro-batch"外推：

| 口径 | 计算 | 结果 |
|---|---|---|
| 每 epoch | 22,941 × 4.54 s = 104,265 s | ≈ **29.0 h** |
| 2 epoch | ×2 | ≈ **58 h** |
| 3 epoch | ×3 | ≈ **87 h（≈3.6 天）** |

即：**当前配置下，仅跑完 1 个 epoch 就需约 29 小时**，3 epoch 约 3.6 天——这正是
本加速文档要解决的问题。

估算边界（口径说明）：

- 计时取自 `train_runtime`，**不含**数据加载/预编码开销。全量 22,941 帧若沿用当前
  "预编码全部样本"的 `_load_dataset`，内存上不可行（见 A3），实际墙钟只会**更长**；
- 32 条样本来自分层字典序抽样，序列长度分布与全量未必一致，此处按"平均每样本耗时"
  一阶外推；
- 以上为**A1 落地前**的原生分辨率读数，只作为"为什么要做 A1"的基线：A1 落地后的实测
  复测值见 A1 节（290.86 s → 90.35 s）；A2（加大 batch）已被证伪，不存在复测值。

## A1. 输入分辨率减半：1600×900 → 约 800×450

- **状态**：已拍板（2026-10-06）。
- **配套**：`max_pixels = 360000`（写入 `configs/sft/sft_smoke_1f.yaml` 的 `model.processor`）。

### 物理直觉

图像在两个维度上各缩小约一半（边长 ×0.5），**面积变为 1/4**。ViT 的 patch 数按面积
线性下降，视觉 token 数同比降到约 1/4 —— 这是纯粹"输入像素变少"带来的收益，
不触碰任何网络结构。

### 使用方式

Qwen2.5-VL 图像处理器在送入 ViT 前做 `smart_resize`：按 `min_pixels`/`max_pixels`
约束 + 原始宽高比，把**原图重采样**到新的 H×W（每边吸附到 factor=28 的倍数，
factor = patch_size(14) × merge_size(2)）。因此：

- **`max_pixels` 就是"在原图上 resize、从根本上降低分辨率"** 的开关；
- `patch_size=14` 是 ViT 结构常量，**不改**（改它等于改网络结构、废掉预训练权重）；
- 默认 `max_pixels=12,845,056` 远大于 1600×900（=1,440,000），故**当前完全不缩放**，
  直接吃满原生分辨率 —— 这正是当前 token 数偏高的根因。

流水线：

```
原图 1600×900 (PIL)
  → smart_resize()          # max_pixels 控制重采样目标面积，patch_size 不变
  → 重采样后 H×W（保宽高比，吸附到 28 的倍数）
  → 按 14×14 切 patch
  → merge_size=2 空间合并
  → visual tokens = patch 数 / 4
```

### 调参影响（真实 processor 实测，源图 1600×900）

| `max_pixels` | 重采样后 | patch | visual tokens | 备注 |
|---|---|---|---|---|
| 12,845,056（原值=不限） | 1596×896 | 7296 | 1824 | 现状基线（未缩放） |
| **360,000（本次定值）** | **784×448** | **1792** | **448** | **边长≈0.5×，面积≈0.25×** |
| 262,144 | 672×364 | 1248 | 312 | 更激进档，备选 |

### 定值依据

- 目标 = "横纵均降为约一半"，即 800×450 ≈ 360,000 像素 → 取 `max_pixels=360000`；
- 实测该值下 `smart_resize` 输出 **784×448**（800/450 无法被 28 整除，被吸附），
  边长比 784/1596≈0.49、448/896=0.50，**符合"横纵各约一半"的原始意图**；
- 收益：patch 7296→1792（**0.246×**）、visual token 1824→448（**0.246×**）、
  序列 2384→约 1008（**0.42×**）。ViT 与解码器同步减负，并释放可观的显存。

### 代价与风险

1. **感知质量**：约 2.0× 线性降采样。源图中 30px 的目标降后约 15px，**远处小目标 /
   施工车等可能受损**，预计会体现在 object / motion_state / risk 轴上。
2. **parity（重要）**：
   - `request_hash_1f` 只覆盖**文本面**（`model_inputs` 序列化结果），分辨率不进 hash，
     故 Step 2 已冻结的样本 JSONL **无需重打**，样本 parity 断言不受影响；
   - 但**训练面与评测面必须同口径**：已跑完的 `runs/S09_base_benchmark/eval_v6/`
     是原生分辨率读数，**与新口径不可直接比较**。用户已裁定：**base benchmark 后测**，
     优先级让位于把 SFT 开销打下来（见本目录决策台账）。
3. **冻结资产纪律**：不修改基座
   `models/Qwen2.5-VL-3B-Instruct/preprocessor_config.json`（冻结资产），
   分辨率以 **config 字段**承载，使其随 config sha 一并登记、可追溯。

### 落地

- 在 `configs/sft/sft_smoke_1f.yaml` 的 `model.processor` 下新增 `max_pixels: 360000`；
- 评测侧（未来的 re-baseline）在 `configs/benchmark/base_1f_v6.yaml` 写入**同一值**，
  保证 train/eval 同口径；
- 变更需登记 config sha 并回填本目录决策台账。

### 适用范围（已定案）

A1 是**全局口径**，不分段适用：Step 3（train32）与 Step 4（overfit128）**都**在
`max_pixels=360000` 下重跑并冻结（见决策台账 D4/D6），S11 内部**不存在**"Step 3 原生 /
Step 4 减半"的分裂；首次以原生分辨率跑出的 train32 已作废留证。

> 回顾：曾把"Step 3 已按原生分辨率跑通并留档"当成既成事实，并列出"① Step 4 改新口径并
> 标注不一致 / ② Step 3/4 统一重跑"两个候选待拍板。该问题在 B7 修复后随 Step 3/4 一并
> 重跑而自然消解，不再需要单独裁定。

## 其余杠杆的结论（原"后续候选项"，已全部定案）

> 本节原为"后续候选项（尚未拍板，占位）"。A2–A5 现在都已有结论，故改写如下——
> 保留在此是为了留下"曾经考虑过什么、最终结论是什么"的痕迹，**不再是待办**。

- **A2 加大 batch —— 已证伪（2026-10-06，裁定见 D5）**。
  原假设：batch=1 占满显存，先靠 A1 释放再上 batch=4/8，预计额外 1.5–2×。
  实测：`bs=2 + accum=2` 与 `bs=1 + accum=4` 同为 16 step，但 runtime **90.35 s → 108.08 s**
  （吞吐 **−16%**）、峰值 reserved **15.08 → 19.01 GiB**。
  **结论：加大 batch 无速度收益、反而吃显存。**
  判据是"方向"：若 bs=1 处于 batch 饥饿区，加 batch 应提升吞吐；实测下降 ⇒ **不饥饿**。
  定案：**维持 batch=1 + grad-accum=4**。另有一条比 A/B 更决定性的长期理由——后续
  4F/多视角时显存预算更紧（4F@A1 序列 ≈2300 vs 1F@A1 1008），富余显存应留给分辨率与
  帧数，而不是换成一个更小的 effective batch。将来若确需更大有效 batch，应由
  **grad-accum 承担**（accum 不占额外显存，batch 才占）。
- **A3 惰性数据集 —— 归属 S12 前置，S11 不做**。
  `cli/sft_train.py::_load_dataset` 现为"预编码全部样本"。按**实测**每样本
  `pixel_values` ≈ **4.2 MB（A1）/ 17.2 MB（原生）** 重估：overfit128 ≈ 0.54 GB
  （S11 无碍），全量 22,941 帧 ≈ **96 GB（A1）/ 394 GB（原生）** ⇒ **全量训练必爆内存**。
  必须改为 `__getitem__` 即时 decode+resize（配 `dataloader_num_workers>0`）。
  它与分辨率决策独立，但同为**全量开工前置**，故立为 S12 的第一件事，不占 S11 交付。
- **A4 缓存冻结 ViT 的图像 embedding —— 方法已立（[S11_vit_embedding_cache.md](S11_vit_embedding_cache.md)），落地留 S12**。
  LoRA 只训语言侧时 ViT 冻结，同图每 epoch 的 encoder 输出不变，可预计算复用。
  收益须按端到端口径看：**1.2×（1F）/ 1.4×（4F），不是 4×**（"4×"只指省掉的那部分
  ViT 算力；ViT 在 1F@A1 下仅占端到端 ≈16%）。实现成本较高，S11 不落地。
  其前置条件"ViT 必须**真的**冻结"曾一度不成立（B7：ViT 的 MLP 被 LoRA 裸后缀连带命中），
  该 bug 已于 2026-10-06 修复并重跑确认（adapter 张量 696→504、`visual` 命中 192→0），
  故**前提现已成立**。
- **A5 epoch / 训练集规模 —— S11 内已定案**：train32 = 2 epoch、overfit128 = 3 epoch
  （规划 §7-F）。全量的 epoch 数与训练集规模属 S12 决策，此处不再占位。
