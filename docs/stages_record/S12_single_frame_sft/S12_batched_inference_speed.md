## 3. 四个效应的分解

1. **权重搬运摊薄（收益来源）**：decode 每步要把全部权重从显存读一遍（带宽受限），
   batch 内多样本共享同一次权重读取。bs=8 时理论摊薄 ~8×。
2. **批内步成本上升（收益打折 ①）**：批量越大，单步要读的 KV/激活越多——
   ms/step 从 54（bs=2）一路涨到 154（bs=32，约 bs=1 的 3 倍）。
   实际摊薄 = bs ÷ (ms/step 比)，bs=8 → 8/1.41 ≈ 5.7×，bs=32 → 32/3.03 ≈ 10.6×。
3. **批内"陪跑"（收益打折 ②，随 bs 恶化）**：HF `generate` 要等**全批**跑完才停，
   批内最长样本决定批耗时。E[max_out] 随 bs 从 193（bs=1 的均值即 max）涨到
   512（bs=32 单批必含跑满档）。bs=32 的实际有效摊薄只剩 10.6 × (mean/max) ≈ 4×。
4. **GPU 利用率佐证（2026-10-07 补录，nvidia-smi 截图时段与 sweep 档位对应）**：
   35% 平台段 = bs=1/2 档，随 bs 上升爬到 60–80%，bs=32 时 98–100% 钉死。
   两段式结论：**bs≤8 在填 kernel 调度空隙（GPU 大量空闲），bs≥16 已接近设备
   饱和**，继续加批只剩带宽摊薄的线性小头——这从设备侧独立印证了 bs=16 定档。
   该图同时解释了 Bug 台账 B1 的"35% 之谜"出处（当时批量路径未生效，35% 正是
   bs=1/2 平台段的正常水平）。口径提醒：nvidia-smi 100% = kernel 无间隙在跑，
   **≠ SM 算力打满**；decode 受显存带宽限制，"打满"时算力利用率也有限。

**结论**：bs 越大边际收益越薄——bs=8→16 还能拿 +22%，bs=16→32 只剩 +13%，
而显存 12.3→17.4 GB、单批方差变大。

## 4. 全量外推（5468 条）与档位建议

| bs | 全量外推 | vs bs=1（15.0h¹） | 备注 |
|---|---|---|---|
| 1 | ~15.0 h | 1× | eval_v6 实际读数 13.6h（冻结面路径略快） |
| 8 | ~5.3 h | 2.8× | 显存最省 |
| **16** | **~4.3 h** | **3.5×** | **推荐生产档位**：收益/显存/方差均衡 |
| 32 | ~3.8 h | 3.9× | 单批样本方差大（本行仅 1 个 batch），收益边际 |

¹ 以 sweep 的 bs=1 档 9.89s/条为基线。

> **推荐 bs=16**：比 bs=8 再快 22%，峰值显存 12.3 GB（32GB 卡余量近 20GB，可容忍
> 更长输入的 4F 面）；bs=32 的 +13% 收益不足以抵偿方差与显存代价。
> 若将来换 4F 面或更长输出，先重跑本 sweep 再定档。

## 5. 口径与局限

- 样本仅 32 条（test 面前 32 个字典序 token），out 长度分布与全集（p50=146 /
  p90=337 / max=512，见 eval_v6 前 164 行）可能有偏；**bs=32 行只有 1 个 batch**，
  统计方差最大，外推时按下界看待。
- `decode tok/s` 为批内摊平值（含陪跑步），不代表单样本延迟；单样本延迟口径见
  `S12_bug_log.md` 读数基线节。
- 全程 GPU 独占；若与训练/其他推理并发，读数作废（B1 的教训之一）。
- parity gate 仍延后（2026-10-07 拍板），本记录只管速度口径；速度与正确性解耦——
  抽查已确认结构一致 + bbox 数值微扰（见 S12_bug_log.md B1 验证节）。
